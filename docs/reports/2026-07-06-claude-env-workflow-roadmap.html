    主要所見の詳細

    ENV-001 @RTK.md import の解決失敗 Critical
    事実
    CLAUDE.md は @RTK.md と @japanese-style-guide.md の2つを参照。本セッションのコンテキストには japanese-style-guide.md の内容は載っているが、RTK.md（トークン削減プロキシ RTK の説明）は載っていない。
    原因
    RTK.md の実体は ~/.claude/RTK.md（git 管理外）にのみ存在し、japanese-style-guide.md は dotdir/.claude/ にのみ存在。@import はシンボリックリンク越しに dotfiles 実体パス基準で解決されるため、~/.claude/ 側にしかない RTK.md が見つからない。
    影響
    RTK の運用ルール（hook による自動書き換えの前提知識）が全セッションで欠落。hook 自体（rtk hook claude）は動いているため実害は限定的だが、「常駐させる」という設計意図が静かに壊れている。
    推奨対応
    RTK.md を dotdir/.claude/ へ移設して git 管理下に置く（1ファイル移動 + リンク）。
    ENV-002 rules/ecc 約1,200行の無差別常駐 Critical
    事実
    本セッション（dotfiles での作業。Web フロントエンド開発ではない）のコンテキストに、rules/ecc/common/ 全10ファイルと rules/ecc/web/ 全7ファイル + README（合計約1,200行）が「全プロジェクト向けグローバル指示」として注入されている。
    原因
    ~/.claude/rules/ 配下の Markdown が自動ロードされる仕組みに対し、ファイルに適用範囲（paths frontmatter）の指定がなく、README のような「人間向け説明文書」まで注入対象になっている。
    影響
    毎セッションのトークン浪費に加え、無関係なルール（例：この dotfiles 作業に Web パフォーマンス予算表）が指示として混入し、指示遵守率を下げる。GMOペパボの実測では同型の整理で起動時トークンを 114,847 → 19,232（83%減）にした事例がある。
    推奨対応
    3択の判断：(a) 各ファイルに paths を付けて適用範囲を絞る、(b) 手順系はスキル（遅延ロード）へ降格、(c) ecc プラグイン本体と重複するものは削除。README は無条件に注入対象から外す。
    ENV-003 スキル説明文の予算超過の疑い High
    事実（外部報告）
    スキル/コマンドの説明文（description）合計には既定 15,000 文字（約4,000トークン）の予算があり、超過分は警告なくシステムプロンプトから脱落する（Jesse Vincent、2025-12 報告）。スキル20個で1個あたり約300字、60個で約130字が上限の計算になる（Zenn 試算）。
    本環境の状況
    ecc（報告値で数百スキル）+ octo（約50スキル+47コマンド）+ superpowers + ARS ほかで、有効スキル総数は数百規模。予算超過はほぼ確実で、「入れているのに Claude から見えていないスキル」が相当数あると推定される（推測 — 計測で確定させる）。
    影響
    スキルの自動発動が静かに壊れる。どれが脱落しているか制御できないため、「たまに効かない」という再現困難な品質劣化として現れる。
    推奨対応
    まず /context で実測。恒久対策はプラグイン削減（ENV-004 と同時）。SLASH_COMMAND_TOOL_CHAR_BUDGET=30000 の拡大は応急処置と割り切る。
    ENV-004 同一役割ツールの多系統重複 High

    確認された重複系統。発動の競合・説明文予算の浪費・選択迷いの3重コストを生んでいます。

    世の中の動向（調査結果の要点）

    3系統の外部調査は、驚くほど同じ結論に収斂しています：「コンテキストは希少資源。常駐を最小化し、必要時に取りに行く」。以下、系統別の要点です。

    • スキル：SKILL.md 本体は150行未満に抑え、詳細は references/ へ（段階的開示）。説明文（description）が自動発動の判定材料のすべて。作成は「評価から始める」— 実タスクでの失敗箇所を特定してから書き、使われ方を観測して反復改善する。
    • サブエージェント：Sonnet をデフォルトにし、Opus 級は複雑推論のみ、Haiku は軽量作業。独立コンテキストにより「多数ファイルを読む作業をメイン会話から隔離する」のが第一の使い道。
    • Workflow（動的オーケストレーション）：.claude/workflows/ に JavaScript + meta ブロックで保存。同時16並列・計1,000エージェントまで。向くのは「多数ファイルの同一チェック」「大規模移行」「複数ソースの交差検証」「複数案の独立立案→評価」。向かないのは単一ファイル編集・3ステップ未満・対話が要る作業。
    • マルチエージェントの費用対効果（研究システムの実測）：単一 Opus 比で評価 90.2% 向上、ただしトークンはチャット比約15倍。性能分散の80%はトークン量で説明される。effort scaling（単純な確認は1エージェント・ツール呼び出し3〜10回、複雑な調査のみ10超のサブエージェント）が運用原則。エージェント間依存が強いタスクと大半のコーディングには不向き。
    • CLAUDE.md / メモリ：200行以下。「事実・規約は CLAUDE.md、複数ステップの手順はスキル」という分担。@import は起動時展開なので常駐コストに直接乗る。
    • コンテキスト管理：遅延ツール読み込み（ToolSearch）は既定で有効。圧縮・構造化メモ・サブエージェント分離が汚染対策の三本柱。大規模作業はコンテキスト80%未満から着手。
    • 説明文予算の「静かな脱落」（最重要）：スキル/コマンド説明文の合計には既定15,000文字の予算があり、超過分は警告なく脱落する。Superpowers 自身も低使用スキルの統合・説明文短縮を実施した。
    • キュレーションの潮流：「量の網羅」から「品質シグナルによる厳選」へ。36.6K スターの wshobson/agents は192エージェントを84の焦点別プラグインに分割し「必要な分だけ入れる」設計へ移行。Memory/Context 管理と Usage/Cost 監視が独立カテゴリ化＝管理自体が主要関心事に。
    • 著名 dotfiles の実践：citypaul は常駐分を約3,000行→約160行へ削減し、29パターンを「必要時に自動発見されるスキル」へ分離。規則の羅列でなく判断フレームワーク（「schema が必要かを判定する5つの質問」等）を常駐させる方針。
    • スキルの検証文化：superpowers は「圧力シナリオ」をサブエージェントに演じさせ、スキルが守られるかテストしてから改訂する（文書への TDD）。信頼できない出所のスキルは導入前にコード・同梱物まで監査せよ（公式も明記）。
    • 自動発動の限界：発動判定は意味的推論で非決定的。誤発動と不発の両方が構造的に発生するため、確実性が要る操作はスラッシュ明示起動へ、危険操作には disable-model-invocation: true を。
    • 3層構造への収斂：CLAUDE.md（薄いエントリポイント）/ rules/（常駐だが paths で範囲限定）/ skills/（呼び出し時のみ）。GMOペパボの実測で起動時トークン 114,847 → 19,232（83%減）。「厚い CLAUDE.md」を擁護する記事は見つからず、争点は「どこまで rules に残すか」へ移行。
    • スキルは「作る」から「育てる」へ：ソニックガーデンは会話履歴から失敗信号を抽出 → Issue 化 → スキル定義を自動修正して PR → 人間はレビューのみ、という毎日の自動改善ループを構築（13日間で40件超の自動改善）。21個運用者の知見では、説明文は先頭に重要語を集中させ（250字で切り詰め）、月1で棚卸し。
    • サブエージェント運用の落とし穴4つ：(1) 会話履歴を引き継がない — 必要情報は指示文かファイルで渡す、(2) 全部並列は罠 — 並列化は全体の30〜40%で十分、(3) 同一ファイルへの複数書き込みで上書き事故 — 「1ファイル=1エージェント」厳守、(4) 5分以上かかるタスクだけ委譲する目安。
    • 個人マーケットプレイス化：COLOPL・Cybozu は「git リポジトリそのものがマーケットプレイス」の最小構成で社内配布を標準化。個人 dotfiles でも成熟スキルをプラグイン昇格させ、別マシン展開を1コマンドにする流れ。
    • hooks は3類型に定着：ガード（PreToolUse + 終了コード2）/ 整形（PostToolUse）/ 通知（Stop・Notification の音分け）。「通知だけに絞る」抑制派も存在。

    フェーズの意図

    1. P0 — 計測と応急処置（合計 1時間以内）

      「基準線を取ってから、確実に壊れているものだけ直す」

      A-1 の計測が以降のすべての判断根拠になります。世の中の実践（ペパボ・海外実測記事）は例外なく「計測が先」でした。A-2 は確認済みの不具合修理で、判断の余地がなく即実施できます。

    2. P1 — 常駐コンテキストの回復（1〜2日）

      「足し算をやめて、引き算で品質を買う」

      環境整理の本丸です。B-1（rules 解体）と B-2（プラグイン棚卸し）は「何を残すか」のトレードオフ判断そのものなので、Fable 5 の推論力が最も費用対効果高く使える場所です。B-2 では ecc の未使用ドメイン（healthcare / logistics / homelab / blockchain 系など）と孤立プラグイン11個が主な候補になります。

    Workflow / Agent 設計方針（フェーズ2の詳細）

    設計原則（公式研究 + コミュニティ実践から）

    1. effort scaling を守る：マルチエージェントはチャット比で約15倍のトークンを使い、それを回収できるのは「並列探索型の高価値タスク」だけです。単純な確認は1エージェント・ツール呼び出し3〜10回で済ませ、10超のサブエージェントは複雑な調査に限定します。
    2. Workflow に向くタスクだけ Workflow にする：多数ファイルの同一チェック（監査）、交差検証、複数案の独立立案→評価。単一ファイル編集・3ステップ未満・対話が必要な作業・依存の強いコーディングには使いません。
    3. サブエージェント指示は4要素を必ず含める：目的 / 出力形式 / 使うツール / タスク境界。会話履歴は引き継がれないため、必要情報は指示文かファイルで渡します。
    4. 書き込み競合を設計で殺す：「1ファイル=1エージェント」を厳守し、並列書き込みが要る場合のみ worktree 分離を使います。
    5. 重複を増やさない：汎用リサーチ系は既存の deep-research スキルが既にあるため新設しません。新設するのは「この環境にしかない資産を束ねるもの」だけです。

    named Workflow 候補（3本）

    WF-1 env-audit — Claude 環境の定期監査 第1弾に推奨
    目的
    スキル説明文の予算消費・重複系統・未使用プラグイン・破損リンク・git↔稼働ドリフトを並列に点検し、1枚の監査レポートに集約する。
    構造案
    並列展開（説明文予算 / 重複検出 / 残置物検出 / ドリフト検出の4エージェント）→ コードで集約 → レポート生成。監査は読み取り専用なので安全に自動化できる。
    選定理由
    本レポートの P1 作業をそのまま再実行可能な形に固定でき、月1ルーチン（D-5）に直結する。最初の Workflow として「作る過程で Workflow 機能自体を学べる」教材性も高い。
    WF-2 doc-review-panel — 文書・論文の多観点並列レビュー
    目的
    論文・レポート・設計書を、観点別レビュアー（論理構成 / 事実確認 / 日本語品質 / 統計・方法論など）が並列でレビューし、所見を敵対的に検証してから統合する。
    構造案
    観点別の並列展開 → 所見ごとに検証エージェント（反証を試みる）→ 生き残った所見のみ集約。ARS の査読エージェントと japanese-output-review スキルを部品として接続。
    選定理由
    ユーザーの実業務（医学研究・文書作成）に直結し、既存資産（ARS・医療コンプライアンススキル・日本語品質システム）を束ねて価値を出せる。Anthropic 公式の「1コマンドから観点別レビュアー並列起動」パターンの応用。
    WF-3 sdd-experiment-sweep — SDD ML 実験の横断監査
    目的
    SDD ML プロジェクトの実験群に対し、リーク検査・実験整合性監査・ログ比較を並列実行し、実験横断の比較マトリクスを生成する。
    構造案
    実験ディレクトリを列挙 → pipeline で各実験に監査エージェント（sdd-experiment-audit / sdd-pre-train-guard の手順を利用）→ 集約して sdd-report-generator へ接続。
    選定理由
    自作スキル最大勢力（SDD/ML 系7個）は現在1つずつ手動起動する設計。「多数対象への同一チェック」という Workflow の得意形そのもので、束ねる価値が最も高い。
