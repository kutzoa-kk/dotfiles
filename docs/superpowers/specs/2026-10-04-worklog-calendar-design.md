# 作業時間のカレンダー記録 設計書

作成: 2026-10-04 · 状態: 実装済み・1日運用での見比べ待ち · 対象: dotfiles の `.bin/worklog/`（導入手順は `.bin/worklog/README.md`）

## 目的

人が作業していた時間と、AI エージェント（Claude Code・Codex）が動いていた時間を、プロジェクトごとに Google カレンダーへ記録する。エージェントの稼働時間だけでは、人がいつ何に時間を使ったかが見えないため、両者を別々の予定として並べる。別プロジェクトでエージェントが並列に動いていたことも、カレンダー上で横に並ぶ予定として見えるようにする。

使い道は工数の把握で、実際の請求には使わない。正確さよりも、カレンダーを見て1日の流れが分かることを優先する。

## 前提として確認した事実

調査は 2026-10-04 にこの Mac（Orca 1.4.183、gog v0.43.0）で行った。

- `orca worktree ps --json` は、Orca の画面で選んでいるプロジェクトを `isActive: true` で返す。Orca の環境変数をすべて外し、`/tmp` から実行しても同じ結果だったので、launchd から使える。
- 同じ出力の `agents[]` に、各エージェントの種類（`agentType`: `claude` / `codex`）と状態（`state`: `working` / `done` など）が入っている。
- `state` は止まったまま残ることがある。2026-10-06 に、ターンを終えた Claude を Orca が 8 時間以上 `working` と返し続けた（ターン終了の通知は届いていた。裏で開発用サーバーを動かしていたペインだけで起きた）。
- `orca terminal list --json` は各端末のタイトルを返し、`tabId:leafId` がエージェントの `paneKey` と一致する。Claude Code はタイトルの先頭に、作業中は回転する記号（`◑` など）、入力待ちでは `✳` を付ける。2026-10-06 に 15 のエージェントで照合し、Orca の `state` と食い違ったのは上のペインだけだった。
- Orca 自身の稼働記録 `orca-stats.json` は、終了の記録が抜けて数日続く区間が残るため使わない（例：dotfiles2 で 68 時間の区間）。
- `orca computer list-windows --app <アプリ>` で、Orca 以外のアプリのウィンドウ名も取れる。Chrome では表示中のタブの題名が返った。osascript による取得は macOS のアクセシビリティ許可がなく失敗した。
- 最後の操作からの経過時間は `ioreg -c IOHIDSystem` の `HIDIdleTime` で取れる。キーボード、マウスの移動、スクロールのいずれでもリセットされる。
- 画面ロック中は、`ioreg -n Root -d1 -a` の `IOConsoleUsers` に `CGSSessionScreenIsLocked` が現れる。解除中はこの項目がない。
- 前面のアプリは `lsappinfo front` と `lsappinfo info` で取れる。
- 上記の取得1回分は 0.24 秒で終わる。
- launchd から動かすと pyenv の Python は使われず、macOS 標準の `/usr/bin/python3`（3.9.6）が使われる。
- gog は専用カレンダーの作成（`create-calendar`）、予定の色指定（`--event-color` 1〜11）、予定への識別用の値の付与（`--private-prop`）に対応している。

## 全体の流れ

launchd で次の処理を定期実行する。

| 処理 | 間隔 | 役割 |
|---|---|---|
| 観測（`sample`） | 60 秒 | その時点の状態を観測ログに1行追記する |
| 書き込み（`sync`） | 15 分 | 直近 48 時間の観測ログから区間を組み立て直し、カレンダーと突き合わせる |

観測と書き込みを分けるのは、判定規則を後から変えても、残っている観測ログから区間を組み直せるようにするためである。

## 観測ログ

`~/.local/state/worklog/samples-YYYY-MM-DD.jsonl` に、1分ごとに次の1行を追記する。

```json
{"ts": "2026-10-04T22:31:00+09:00",
 "idle_sec": 12,
 "locked": false,
 "front_bundle": "com.google.Chrome",
 "front_app": "Google Chrome",
 "window_title": "論文タイトル - Google Scholar",
 "orca_project": "dotfiles2",
 "agents": [{"project": "dotfiles2", "type": "claude", "task": "Pull反映"},
            {"project": "proj-b", "type": "codex", "task": "codex"}]}
```

- `orca_project` は `isActive` のプロジェクトの `repo` 名。Orca が起動していなければ `null`。
- `agents` は `state` が `working` のエージェントだけを並べる。ただし端末のタイトルが `✳` で始まるものは、Orca の `state` が止まったまま残った場合とみなして除く。
- `task` は端末のタイトルから先頭の記号と空白を除いたもの（Claude Code が付けるタスク名）。タイトルが取れないときは `null`。
- `window_title` は Orca が起動していないと取れないので `null` になる。
- 30 日より古いファイルは `sync` が削除する。

## 人の作業の判定

### アプリの分類

前面のアプリを、設定ファイルのバンドル ID の一覧で次のように分ける。

| 分類 | 初期値 | 記録先 |
|---|---|---|
| プロジェクト作業 | Orca、Safari、Preview、Word、Acrobat、Obsidian | その時点で Orca が選んでいるプロジェクト |
| その他の作業 | Chrome、VS Code、PowerPoint、Excel、Slack | 「その他」 |
| 対象外 | 上記以外 | 記録しない |

ウィンドウ名が除外パターン（初期値は YouTube、TVer、Netflix などの動画サイト）に当たる1分は、分類に関係なく記録しない。プロジェクト作業のアプリでも、`orca_project` が `null` の1分は記録しない。

### 操作が止まった区間の扱い

キーボードやマウスに触らずに文書を読んでいる時間を拾うため、操作が止まった区間を、その後に何が起きたかで分類する。

1. 操作中の1分（`idle_sec` が 60 未満）は作業とする。
2. 操作が止まった後、同じアプリ・同じウィンドウ名のまま操作が再開された場合は、止まっていた間も読んでいたとみなし、作業とする。ただし止まっていた時間が 30 分を超えた場合は離席とする。
3. 画面ロックで終わった場合、または別のウィンドウで再開された場合は、最後の操作から 2 分後までを作業とし、残りを離席とする。
4. 観測ログが 2 分以上空いた場合（Mac のスリープなど）は、その間を離席とする。

規則 2 は操作が再開されるまで決まらない。判定が決まっていない区間は、規則 3 と同じく最後の操作の 2 分後までを仮の終わりとして書き込み、決まった時点で延長する。

## エージェントの稼働の判定

`agents` に現れたプロジェクトとタスクの組ごとに、その1分を稼働とする。同じプロジェクトでも、タスクが違えば別の予定にする。同じタスクで複数のエージェントが同時に動いていれば、予定は1本にまとめる。`task` のない古い観測行は、タスクなしの1つの組として扱う。

## 区間のまとめ方

人の作業（プロジェクトごと・その他）とエージェントの稼働（プロジェクトとタスクの組ごと）のそれぞれで、次の順に処理する。

1. 隣り合う作業中の1分をつないで区間にする。
2. 区間どうしの切れ目が 5 分未満ならつなぐ。
3. 3 分未満の区間は捨てる。

## カレンダーへの書き込み

### 予定の形

人の作業は「作業ログ（人）」、エージェントの稼働は「作業ログ（AI）」の2つの専用カレンダーに分けて書く。人か AI かはカレンダーで分かるので、予定名には作業の中身だけを書く。予定は「予定なし」（`--transparency=transparent`）として作り、他の人から見た空き時間をふさがない。

| 種類 | 予定名 | 色 | 説明欄 |
|---|---|---|---|
| 人・プロジェクト | `dotfiles2` | プロジェクトの色 | Orca 以外で読んでいたウィンドウ名と分数（多い順に最大 5 件） |
| 人・その他 | `その他` | グラファイト（8）で固定 | アプリ名とウィンドウ名と分数（多い順に最大 5 件） |
| エージェント | タスク名（例：`Pull反映`。タスク名がなければプロジェクト名） | プロジェクトの色 | プロジェクト名、エージェントの種類と最大同時数（例：`dotfiles2 / claude ×2`） |

プロジェクトの色は `local.json` で決める。設定のないプロジェクトには、名前から 8 以外の 1〜11 の色を自動で割り当てる。

ウィンドウ名は Google カレンダーに送られる。見せたくない題名は除外パターンに足す。

### 突き合わせ

各予定には `--private-prop worklog_key=<キー>` を付け、作成済み予定の控え `~/.local/state/worklog/events.json`（キー → 予定 ID・書き込んだカレンダー・終了時刻・予定名・説明欄）に記録する。キーは人なら `human|<プロジェクト>|<開始時刻>`、エージェントなら `agent|<プロジェクト>|<タスク>|<開始時刻>`。`sync` は直近 48 時間について次のように突き合わせる。

- 組み立てた区間のキーが控えにない → 予定を作成する。
- キーはあるが終了時刻・予定名・説明欄のどれかが違う → 控えに記録したカレンダーの予定を更新する。
- 控えにあるが組み立て直した結果に現れない → 控えに記録したカレンダーから予定を削除する。

書き込んだカレンダーの記録がない控えは、人のカレンダーにあるものとして扱う。

48 時間より前の予定には触れない。同じ区間を何度送っても予定は増えない。

### 初回の準備

各 PC で gog の Google 認証を済ませ、`~/.config/worklog/local.json` に書き込み先のアカウントを書く。最初の PC だけ `python3 .bin/worklog/worklog.py init-calendar` で2つの専用カレンダーを作成し、表示された ID を `local.json` の `calendar_id`（人）と `agent_calendar_id`（AI）に書く。`init-calendar` は ID が未設定のカレンダーだけを作る。2台目以降の PC では同じ ID を書く。

## 置き場所

| 置き場所 | 中身 | git |
|---|---|---|
| `.bin/worklog/worklog.py` | 入口（`sample` / `sync` / `init-calendar`） | 管理する |
| `.bin/worklog/` の各モジュール | 観測、判定と区間化、カレンダー連携 | 管理する |
| `.bin/worklog/config.json` | アプリの分類、除外パターン、各しきい値、タイムゾーン | 管理する |
| `.bin/worklog/launchd/*.plist.template` | launchd 設定のひな形 | 管理する |
| `.bin/tests/test_worklog_*.py` | 単体テスト | 管理する |
| `~/.config/worklog/local.json` | 書き込み先のアカウント、カレンダー ID、プロジェクトの色 | 管理しない（PC ごと） |
| `~/.local/state/worklog/` | 観測ログ、予定の控え、エラーログ | 管理しない（PC ごと） |
| gog の Google 認証 | | 管理しない（PC ごと） |

dotfiles リポジトリは公開されているため、メールアドレス、カレンダー ID、プロジェクト名は git に入れない。

Python 標準ライブラリだけで書き、`/usr/bin/python3`（3.9）で動くようにする。

複数の PC で使うが、同時に同じカレンダーへ書き込むことはない前提で、PC の区別はしない。

## 登録と解除

`Makefile` に次の目標を足す。

- `make worklog-install`：ひな形の `__HOME__` と `__WORKLOG__`（`.bin/worklog` の絶対パス）をその PC の値に置き換えて `~/Library/LaunchAgents/local.worklog.sample.plist` と `local.worklog.sync.plist` を書き出し、`launchctl bootstrap gui/$(id -u)` で登録する。
- `make worklog-uninstall`：`launchctl bootout` で登録を外し、書き出した plist を消す。
- `make test-worklog`：単体テストを実行する。

launchd 設定にパスを直接書かないので、ユーザー名や dotfiles の置き場所が違う PC でも同じ手順で入る。

## 失敗したときの扱い

- Orca が起動していない：`orca_project`・`window_title` を `null`、`agents` を空にして記録する。プロジェクト作業の時間は記録されないが、その他の作業は記録される。
- 端末の一覧が取れない：タイトルによる除外をせず、Orca の `state` だけで判定する。タイトルが読めないことは、止まっている証拠にならないため。
- gog の呼び出しが失敗した：その予定の控えを更新せず、`~/.local/state/worklog/errors.log` に記録して次の回にやり直す。
- 観測ログの行が壊れている：その行を飛ばし、エラーログに記録する。

## 確かめ方

- 判定と区間化：人工的な観測ログを入力にした単体テスト。対象は、操作再開による区間のつなぎ（30 分ちょうどの境界を含む）、ロックで終わる場合、別ウィンドウでの再開、スリープによる欠落、除外パターン、その他の作業の振り分け、同一プロジェクトで並列に動くエージェント、5 分未満の切れ目と 3 分未満の区間。
- カレンダー連携：gog の呼び出しを差し替え、作成・更新・削除が正しく出るかを単体テストで確かめる。
- 実機：この Mac で1日動かし、カレンダーの予定と実際の作業を見比べる。

## 対象外

- Orca の外で動かしたエージェント（iTerm で起動した Claude Code、クラウドで動くエージェントなど）
- 紙や別の端末で読んでいた時間
- 請求用の集計や出力
