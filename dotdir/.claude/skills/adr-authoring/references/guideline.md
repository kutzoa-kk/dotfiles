# ADR 執筆規約

ADR の書き手とレビュー側が同じ基準で読むための規約です。強度は2段階にします。

- **MUST**：満たさなければ採用しない
- **SHOULD**：原則として満たす。外すときは、外す理由を ADR の中で説明する

作例はすべてこの規約のために作ったもので、実在の ADR からは引用していません。実在の ADR は後で無効になり、規約の中に古い決定が残るためです。

## A. 参照情報の置き場所

| ID | 強度 | 規約 |
|---|---|---|
| A-1 | MUST | 本文にチケット番号・PR 番号・Issue 番号・担当者名を書かない。経緯の追跡は git とチケット側に任せる |
| A-2 | MUST | 他の ADR との関係（置き換え・依存・関連）は「関連 ADR」欄にまとめる。本文の途中に散らさない |
| A-3 | SHOULD | 外部の資料・論文・公式文書は「References」欄にまとめ、本文からは短い名前で指す |

- NG：「#123 の議論を受けて、田中さんの案で進める」
- OK：「書き込みが集中する時間帯にロックの待ちが増える（References：負荷試験の結果）」

## B. 参照の指し方

| ID | 強度 | 規約 |
|---|---|---|
| B-1 | MUST | 行番号で参照しない。ファイルは編集で行がずれる |
| B-2 | MUST | 他の ADR の中身は「ADR 番号＋節名」で指す。文言の引用だけで指さない |

- NG：「`config.yml` の 42 行目の設定を使う」「ADR-0003 の『キャッシュは使わない』に従う」
- OK：「`config.yml` の `cache.ttl` を使う」「ADR-0003 の Decision に従う」

## C. 事実と根拠

| ID | 強度 | 規約 |
|---|---|---|
| C-1 | MUST | Context と Decision に書く事実は、実際のコード・設定・一次資料と照らして確かめる。確かめられない事実は書かない |
| C-2 | SHOULD | 数値や比較の結果には出どころ（資料のパス、計測の条件）を添える |
| C-3 | MUST | その ADR だけを読んで、決定と理由が分かるようにする。「前述の議論のとおり」「例の問題」のように、ADR の外にある文脈に頼らない |
| C-4 | SHOULD | Context は一般論でなく、このプロジェクトで起きている問題を書く |

- NG（C-1）：「定例会議で、この方式のほうが速いと分かった」。根拠が会議にしか残らず、後から確かめられない
- OK（C-1）：「100 件の一括登録で、方式 A は 12 秒、方式 B は 3 秒だった（References：計測スクリプトと結果）」
- NG（C-4）：「一般に、マイクロサービスは拡張しやすい」
- OK（C-4）：「解析の処理が API の応答を待たせ、計測会の当日に画面が止まった」

## D. 決定の範囲

| ID | 強度 | 規約 |
|---|---|---|
| D-1 | MUST | 移行計画・作業手順・進捗・タスク表・日程を書かない。それらは計画書やチケットに置く |
| D-2 | MUST | 1つの ADR には1つの決定だけを書く。決定が2つあれば ADR を分ける |
| D-3 | SHOULD | 適用範囲（Scope）と「決定しないこと」を書く。「決定しないこと」には、どこで決めるか（委譲先）を実在する名前で書く |
| D-4 | SHOULD | Decision は、実装の選び方を縛りすぎない粒度で書く |

D-4 の判定の問い：「決めた実現方式を別の方式に差し替えたとき、Decision の文を書き換える必要があるか」。書き換えが必要なら、その記述は実装の細部です。設計書・仕様書・コードのコメントへ移し、ADR には方式を選んだ理由を残します。

- NG（D-1）：「[ ] 第1週にテーブルを作る　[ ] 第2週にデータを移す」
- OK（D-1）：「移行中も読み取りを止めないため、新旧のテーブルを一定期間並べて動かす方式を選ぶ」
- NG（D-4）：「接続の上限は 50、待ち時間は 3 秒、再試行は 2 回とする」
- OK（D-4）：「接続数に上限を設け、上限に達したら待たせる方式にする。値は設定ファイルで決める」
- NG（D-3）：「認証の方式は今回は決めない」
- OK（D-3）：「認証の方式は決めない。ADR-0008 で決める」（委譲先が実在すること）

## E. ADR どうしの整合

| ID | 強度 | 規約 |
|---|---|---|
| E-1 | MUST | 状態を変えたら、一覧（`README.md` など）の状態も同じ変更でそろえる |
| E-2 | MUST | 置き換え・廃止のときは、古い ADR を「いま有効な決定」として指している ADR 以外の文書（CLAUDE.md・README・設計書）を検索し、置き換えなら新しい ADR を指すように直す。後継のない廃止なら、その参照を外すか、廃止されたことを書く。他の ADR の本文は書き換えず、その時点の参照として残す（E-4） |
| E-3 | MUST | 置き換えは双方向に書く。新しい ADR に `Supersedes ADR-NNNN`、古い ADR に `Superseded by ADR-MMMM`。古い ADR の状態を変えるのは、新しい ADR を `Accepted` にするときで、同じ変更の中で行う。新しい ADR が `Proposed` のうちは、古い ADR が有効な決定のまま |
| E-4 | MUST | 採用後の ADR は本文を書き換えない。直してよいのは状態欄と関連 ADR 欄だけ。決定が変わったら新しい ADR を書き、後継なしで無効にするなら状態を `Deprecated` にして理由を関連 ADR 欄に書く |

## F. 表記と語彙

| ID | 強度 | 規約 |
|---|---|---|
| F-1 | SHOULD | 見出しと状態の値は雛形（`template.md`）にそろえる。リポジトリに既存の形があれば、その形にそろえる |
| F-2 | SHOULD | 同じものを同じ名前で呼ぶ。言い換えない |
| F-3 | SHOULD | 「最終更新日」「現在の担当」「今のバージョンは」など、すぐ古くなる情報を書かない。日付は決定日（`Date`）だけにする |

## G. 採用前の点検

| ID | 強度 | 規約 |
|---|---|---|
| G-1 | MUST | `Accepted` にする前に、「未確定」「TBD」「要確認」を残さない。決められない点は D-3 の「決定しないこと」に移す |
| G-2 | SHOULD | セキュリティ・個人情報・データの保存に関わる決定では、守る対象・脅威・残る危険を Consequences に書く |
| G-3 | SHOULD | 検討した他の案と、採らなかった理由を Alternatives Considered に書く |
