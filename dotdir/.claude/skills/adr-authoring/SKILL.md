# ADR の執筆と更新

ADR は「何を決め、なぜそう決めたか」だけを残す文書です。移行の段取り、進捗、実装の細部は ADR に書かず、それぞれの置き場所へ回します。規約の本文は [references/guideline.md](references/guideline.md) の1か所だけに置き、ほかのスキルや文書には規約を書き写さず、この場所を参照させます。

## 手順

作業の種類ごとに、次の順で進めます。どの作業でも、先に `references/guideline.md` を読みます。

### 新しく書く

1. 対象のリポジトリの ADR 置き場（`docs/adr/`・`docs/decisions/`・`adr/`）と、既存の ADR、一覧（`README.md` など）を読みます。既存の番号の付け方・ファイル名・見出しが雛形と違えば、そのリポジトリの形に合わせます。
2. 置き場がなければ `docs/adr/` を作り、最初の ADR は「ADR で決定を記録する」という決定にします（雛形の末尾の作例）。呼び出し元のスキルや依頼が最初の ADR の内容やファイル名を指定していれば（mvh-setup のハーネス採用の ADR など）、そちらを優先します。
3. [references/template.md](references/template.md) を写して書きます。状態は `Proposed` から始めます。
4. Context に書く事実は、実際のコード・設定・一次資料で確かめます（C-1）。会話や会議だけにある根拠は、確かめられる形（資料のパス、計測結果）にするか、書きません。
5. 書き終えたら、下の「自己点検」を行います。

### 状態を変える・置き換える・廃止する

ADR は、決定が採用（`Accepted`）された後は本文を書き換えません。決定が変わったら新しい ADR を書き、後継なしで無効にするだけなら新しい ADR は書きません。どちらの場合も、古い ADR で直すのは状態欄と関連 ADR 欄だけです。

1. 新しい ADR を `Proposed` で書き、関連 ADR 欄に `Supersedes ADR-NNNN` と置き換え元を書きます。この時点では古い ADR に触りません。新しい ADR が採用されるまでは、古い ADR が有効な決定です。
2. 新しい ADR を `Accepted` にするときに、同じ変更で古い ADR の状態を `Superseded by ADR-MMMM` にし、関連 ADR 欄に置き換え先を足します（E-3）。新しい ADR が採用されずに終わったら、古い ADR はそのままにします。
3. 廃止だけで後継がないときは、状態を `Deprecated` にし、理由を関連 ADR 欄に1文で書きます。欄を削っていたら足します。
4. 一覧の状態をそろえます（E-1）。CLAUDE.md・README など ADR 以外の文書が古い ADR を「いま有効な決定」として指していれば、置き換えなら新しい ADR を指すように直し、後継のない廃止ならその参照を外すか「この決定は廃止された」と書き直します。他の ADR の本文は書き換えません。その時点の参照として残し、読み手は古い ADR の状態欄で、置き換えられたのか（後継の番号）、廃止されたのかを確かめます（E-2・E-4）。

`Proposed` の ADR は、採用までは本文を直してかまいません。採用前に「未確定」「TBD」を残さないことを確かめます（G-1）。

### 点検する（レビュー）

`references/guideline.md` の規約を上から当て、違反を「規約 ID・該当箇所（節名）・直し方」の形で報告します。MUST の違反は直すまで採用しません。SHOULD を外しているときは、外す理由が書かれているかを見ます。依頼が点検だけなら、ファイルは直しません。

## 自己点検

書いた・直した ADR について、次を確かめます。

- 本文にチケット番号・PR 番号・Issue 番号・担当者名・進捗が入っていない（A-1・D-1）
- 関連 ADR は関連 ADR 欄に、外部資料は References 欄にまとまっている（A-2・A-3）
- 他の ADR は「ADR 番号＋節名」で指し、行番号で指していない（B-1・B-2）
- この ADR だけを読んで、決定と理由が分かる（C-3）
- Decision を別の実現方式に差し替えても、Decision の文を書き換えずに済む（D-4）
- 「決定しないこと」に、委譲先が実在する名前で書かれている（D-3）
- 状態を変えたなら、一覧と、ADR 以外の文書からの参照も直した。他の ADR の本文は書き換えていない（E-1・E-2）
- 古い ADR を `Superseded` にしたのは、新しい ADR を `Accepted` にしたのと同じ変更の中である（E-3）

## 他のスキルとの関係

- repo-hygiene-audit：古い説明文を ADR に変換すると判断したら、このスキルで書きます。
- mvh-setup・ml-experiment-traceability：最初の ADR や雛形を置くときは、このスキルの雛形を使います。

規約は、ADR のレビューで同じ指摘が繰り返されたら `references/guideline.md` に足していきます。足すときは、既存の規約と重ならないかを先に検索します。

参考にした考え方：TOKIUM「AI に書かせた ADR を読みやすくする執筆ガイドライン」（https://zenn.dev/tokium_dev/articles/adr-authoring-guideline）。カテゴリ A〜G と MUST/SHOULD の2段階は記事に倣い、規約の文面と作例はこのスキル用に書いています。
