# Backlog 書き込みの運用ルール

**前提：** コマンドの使い方は using-bee、Backlog記法は backlog-notation に従う。このスキルは、書き込むときに守る手順だけを定める。

Backlog への書き込みは、担当者やウォッチしているメンバーへすぐ通知が届く。通知とメールは後から消せないので、書き込みは「調べる → 下書きを見せる → 承認後に実行 → 反映を確かめる」の順で進める。

## 1. 書き込む前に下書きを見せ、承認を得る

対象は、起票・編集・状態変更・クローズ・コメント・削除、ドキュメント・Wiki・プルリクエストの作成と編集、`bee api` の POST/PUT/PATCH/DELETE。一覧・閲覧・ID 確認などの読み取りは確認なしで実行してよい。

ID を調べ終えてから、次の形で1回にまとめて見せ、「この内容で実行してよいですか」と聞いて止まる。

````
対象：WEBAPP-482（新規なら「WEBAPP に WEBAPP-482 の子課題を新規作成」）
変更：状態「処理中」→「処理済み」、コメントを追加
本文：
（投稿する本文をそのまま全文）
実行するコマンド：
```sh
bee issue edit WEBAPP-482 --status 3 -c "$(cat <一時ファイル>)" --yes
```
````

| 言い訳 | 実際 |
|--------|------|
| 依頼で明示されているから確認は要らない | 依頼にあるのは操作だけで、本文・完了条件・件名は AI が書いたもの。チームが読む前に本人が見る |
| 後から編集で直せる | 本文は直せても、送られた通知とメールは消えない |
| 操作が多いので1つずつ聞くと煩わしい | 確認は全操作をまとめて1回にする。確認を省く理由にはならない |

## 2. 名前ではなく ID を渡す

状態・種別などは名前を受け付けない。ID はプロジェクトごとに違うため、毎回調べる。

プロジェクトによっては「保留」「アイデア」「キャンセル」のような独自の状態がある。「完了以外」のような条件は、状態一覧の全 ID から除くものだけを外して指定する。標準の4つ（未対応・処理中・処理済み・完了）だけだと決めつけない。

| フラグ | 渡す値 | 調べ方 |
|--------|--------|--------|
| `--status` / `-S` | 状態 ID | `bee status list -p PROJ --json id,name` |
| `--type` / `-T` | 課題種別 ID | `bee issue-type list -p PROJ --json id,name` |
| `--priority` / `-P` | `high` / `normal` / `low` のどれか | 固定値（「中」は不可） |
| `--parent-issue` | 親課題の数値 ID（キーではない） | `bee issue view PROJ-123 --json id` |
| `--assignee`（`-a` は create のみ） | ユーザーの数値 ID か `@me` | `bee project users -p PROJ --json id,name` |
| `--category` / `--milestone` | 各 ID | `bee category list -p PROJ --json` / `bee milestone list -p PROJ --json` |

## 3. 本文の渡し方

- 本文はスクラッチパッドの一時ファイルに書き、`"$(cat <ファイル>)"` で渡す（改行が潰れない）。フラグ名はコマンドで違う。
  - 課題の説明：`bee issue create/edit` の `-d`
  - 更新と同時のコメント：`bee issue edit` の `-c`
  - コメントだけ追加：`bee issue comment` の `-b`
  - ドキュメント・Wiki・プルリクエスト：`-b`（Wiki の題は `-n`、ほかは `-t`）
- 絵文字などの4バイト文字を入れない（`Incorrect String` エラーになる）。依頼文に絵文字があっても本文には書かない。
- チェックボックス（`- [ ]`）は課題の説明欄でだけ描画される。コメントでは箇条書きにする。
- 日本語のです/ます体で書く。記法（Markdown か Backlog記法か）は using-bee の手順で確かめる。
- 非対話の実行なので、必須項目はすべてフラグで渡し、`--yes` を付ける。

## 4. 課題本文のひな形

```markdown
## 概要
なぜ必要か、どこで気づいたかを1〜3文（子課題なら親課題のキーを書く）

## 完了条件
- [ ] 第三者が確かめられる形の条件（4〜8項目）

## 参考
関連する課題キー・プルリクエスト・URL
```

Backlog記法のプロジェクトでは、見出しを `**` に置き換える。

## 5. まとめて変える操作

マイルストーンの付け替え、カテゴリの一括付与、通知の一括既読など、複数の対象をまとめて変える依頼は次の順で進める。

1. 対象を漏れなく集める。`bee issue list` は初期設定で20件までしか返さないので、`-L 100 --offset 0`、`--offset 100` …と、返った件数が100未満になるまで取得する。`bee issue count` で絞り込めるのは状態・担当者・優先度・キーワード・日付だけで、マイルストーンやカテゴリを付けると `unknown option` で失敗する。その場合は、ページ送りで数えた件数を使う。
   - `bee issue edit` の `--milestone` と `--category` は、指定した ID で置き換わる（追加ではない）。今の値を残したいときは、今の ID も一緒に指定する。
2. 承認を求めるときは、対象の件数、変更内容、対象の一覧（課題キーとタイトル）を見せる。一覧が長いときはスクラッチパッドのファイルに書き出し、その場所を示す。
3. 実行は1件ずつ行う。失敗した対象があっても止めずに記録し、最後に成功と失敗の件数と、失敗した課題キーを報告する。`API rate limit exceeded` が出たら、表示された時刻まで待ってから残りを続ける。
4. プロジェクトをまたぐ操作では、対象のプロジェクトキーを指定して絞る。参加している全プロジェクトへ問い合わせると、回数制限に触れやすい。

## 6. 実行後に確かめてから報告する

書き込んだら `bee issue view PROJ-123 --json status,parentIssueId,description` などで反映を確かめ、確かめた内容だけを報告する。実行していない操作を実行済みと書かない。

`No space configured` や `AuthenticationError` が出たら、ユーザーに `! bee auth login` の実行を頼む（対話入力が要るので代行しない）。

## よくある間違い

| 間違い | 正しくは |
|--------|----------|
| `--status 処理済み` | `bee status list` で調べた ID（例：`--status 3`） |
| `--parent-issue WEBAPP-482` | `bee issue view WEBAPP-482 --json id` の数値 ID |
| `--issue-type タスク` | `--type <ID>`（`--issue-type` というフラグは無い） |
| `--priority 中` | `--priority normal` |
| `bee issue create --body ...` | 課題の説明は `-d`（`--body` は無い） |
| 依頼が明確なので確認なしで起票 | 下書きを見せて承認を得てから実行 |
| 一覧の先頭20件だけを一括変更の対象にする | ページ送りで全件を集め、件数を見せてから実行 |
