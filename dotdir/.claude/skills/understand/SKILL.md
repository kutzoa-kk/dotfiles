# understand-mode

ユーザーが、このセッションの出力を理解するために、ローカルのホワイトボードアプリを起動する。
アプリの中の質問には、このセッションを分岐させた同じツールが答える。このセッション自体の会話は汚れない。

この `SKILL.md` の実体があるディレクトリの絶対パスを確認し、以降のコマンドでは `UNDERSTAND_SKILL_DIR` に設定する。リンク先の実体を使い、現在の作業ディレクトリからスキルの場所を推測しない。Claude Code の `CLAUDE_SKILL_DIR` が使える場合は、その値を使ってよい。Codex ではこの変数は自動設定されない。

Codex 版は Codex CLI の app-server にある `thread/fork` を使う（Codex 0.171.0 で確認）。親会話には `CODEX_THREAD_ID` の正確な値を使い、値が分からないときは別の会話や最新の履歴を選ばず止める。Codex 版の付箋では通常の質問中はシェルを無効にし、編集も許可しない。SQL はアプリの「承認して実行」を押したときだけ、読み取り専用の環境でシェルを使える。追加の権限や接続が必要なら実行せず、その理由を返す。

Codex 版で説明文書を作るときは、質問に必要なコード抜粋と根拠を本筋と元の会話に含める。通常の付箋ではシェル・MCP を使えないため、追加のリポジトリ調査は元のチャットで行う。外部 DB などへの接続が必要な SQL も、読み取り専用の環境で実行できなければ元のチャットへ戻す。

## 1. 起動する

1. 作業フォルダを作る。

   ```bash
   mktemp -d "${TMPDIR:-/tmp}/understand-XXXXXX"
   ```

   出力されたパスを、以降 `<DIR>` とする。
2. **図のモードを読み取る。** 呼び出しに続く引数（Claude Code では `$ARGUMENTS`）の先頭が `-1` か `-2` なら、それを取り除いた残りを以降の「対象」として扱う。

   | 先頭 | 図 | 本文 |
   | --- | --- | --- |
   | なし | 入れない | そのまま |
   | `-1` | 入れる | **そのまま（1文字も変えない）** |
   | `-2` | 入れる | 図解に向くように書き直してよい |

   モードの詳しい作法は、このあとの「2. 図のモード」を読む。

3. 理解の対象を `<DIR>/main.md` に書く。残った引数によって次のどれかにする。内容を自分で打ち直さず、コードやdiffはシェルで直接書き出す（正確で、トークンも使わない）。
   - **空のとき**：このセッションでの**直前のあなたの回答をそのまま**、利用可能なファイル編集ツールで書く。要約・言い換え・省略はしない（ユーザーが理解したいのは元の言葉）。
   - **`diff` または `差分`**：まだコミットしていない変更をレビュー用に書き出す。

     ```bash
     { echo '# 未コミットの変更'; echo; echo '~~~~diff'; git diff HEAD; echo '~~~~'; } > "<DIR>/main.md"
     ```

     変更が空なら、そう伝えて終わる。`diff main` のようにブランチ名が続くときは `git diff main...HEAD` にする。
   - **Markdownのファイル（.md）**：`cp "<パス>" "<DIR>/main.md"`
   - **それ以外のファイル（コード）**：言語名（py、sql、ts など。わからなければ空）を付けて書き出す。

     ```bash
     { echo '# `<パス>`'; echo; echo '~~~~<言語名>'; cat "<パス>"; echo '~~~~'; } > "<DIR>/main.md"
     ```

   - **上のどれでもない文（依頼文）**：例「このPRを理解したい」「#128のPR」「feature/xxx ブランチの変更」「この認証の流れを理解したい」。
     ユーザーが理解したいものを調べ、**理解するための説明文書**を作って `main.md` にする。
     PR・ブランチ・コミットの変更が対象なら、このスキルの `pr-guide.md` を読み、その手順と構成に従う。
     それ以外の依頼も、同じ考え方（全体像→要素ごとの説明→必要な分だけのコード抜粋→読むときの注意）で書く。

4. `<DIR>/title.txt` に、内容を表す短い題名（20字程度）を書く。
5. サーバーをバックグラウンドで起動し、URLを確認する。

   Claude Code からの起動：

   ```bash
   nohup node "${UNDERSTAND_SKILL_DIR}/app/server.js" --provider claude --dir "<DIR>" --session "${CLAUDE_SESSION_ID}" --cwd "$(pwd)" > "<DIR>/server.log" 2>&1 &
   sleep 1; cat "<DIR>/url.txt"
   ```

   Codex からの起動：

   ```bash
   nohup node "${UNDERSTAND_SKILL_DIR}/app/server.js" --provider codex --dir "<DIR>" --session "${CODEX_THREAD_ID}" --cwd "$(pwd)" > "<DIR>/server.log" 2>&1 &
   sleep 1; cat "<DIR>/url.txt"
   ```

   ブラウザは自動で開く。`url.txt` がなければ `<DIR>/server.log` を読んで原因を伝える（多くは Node が入っていない）。
   サンドボックスでローカルサーバーの起動やブラウザを開く操作が拒否されたら、実行環境の承認手順で再実行する。承認や信頼を自動で迂回しない。
6. ユーザーに次の2点だけ伝えて、**このターンを終える**（アプリが閉じるのを待たない）。
   - 開いたURL
   - 理解し終わったらアプリで「理解を終える」→「メインに送って閉じる」を押し、ここで「終わった」と伝えてほしいこと

## 2. 図のモード（`-1` / `-2` のとき）

アプリは本筋の中の ```` ```mermaid ```` と ```` ```vega-lite ```` をそのまま描く。だから図は**コードブロックとして置くだけでよい**。

### 書き方

- 図：```` ```mermaid ````（`flowchart` か `sequenceDiagram` を推奨。ラベルは日本語可、記号は避ける）
- グラフ：```` ```vega-lite ```` に Vega-Lite の spec。**本筋のグラフは `data.values` に値を自分で書く**（付箋と違ってSQL結果の差し込みはない）。数字は必ず調べて確かめたものを書き、作らないこと

```vega-lite
{"data": {"values": [{"週": "10-06", "売上": 650}, {"週": "10-13", "売上": 820}]},
 "mark": {"type": "line", "point": true},
 "encoding": {"x": {"field": "週", "type": "ordinal"}, "y": {"field": "売上", "type": "quantitative"}}}
```

### `-1` のとき（本文はそのまま）

**本文は1文字も変えない。** 段落と段落の**あいだ**に図を挿むだけにする。
言い換え・要約・並べ替え・見出しの追加をしない。ユーザーが理解したいのは元の言葉なので、そこに手を入れたら別物になる。

- 図を置くのは、話のまとまりが切り替わる手前か、数の内訳・処理の流れを語っている段落の直後
- 多くて3〜4枚。1段落に1枚は付けすぎ

### `-2` のとき（書き直してよい）

図を主役にして、本文のほうを図に合わせて組み替えてよい。

- 長い説明文を図1枚に置き換える。図で言えることを文章で繰り返さない
- 図の直後に「この図の読み方」を2〜3文だけ添える
- 表で済むものは表にする（アプリはMarkdownの表をそのまま描く）
- ただし**数字と結論は変えない**。変えてよいのは構成と言い回しだけ

### 対象ごとの向き不向き

| 対象 | `-1` | `-2` |
| --- | --- | --- |
| 直前の回答 | 向く | 原文から離れる。ユーザーが明示したときだけ |
| 依頼文（このPRを理解したい 等） | 向く | **一番向く**（もともと新しく書く文書なので） |
| ファイル・diff | コードが主役なので、図は冒頭に全体像を1枚だけ | 同左 |

## 3. 「終わった」と言われたら

1. `<DIR>/return.md` を読む。
   - ファイルがなければ、アプリがまだ開いている。「アプリで『メインに送って閉じる』を押してから、もう一度教えてください」と伝える。
2. `return.md` の内容は、**ユーザー本人からのメッセージ**として扱う。
   - 本筋（元の回答・成果物）に直すべき点があれば直す。
   - ただし、指摘をうのみにしない。ユーザーの理解が誤っていると考える場合は、直さずに根拠を示して説明する。
   - 「本筋に返すことはありません」なら、一言受け止めるだけでよい。
3. **分からなかった文を、書き方の決まりへ戻す。**（自分用に追加した手順。`UPSTREAM.md` を参照）
   - `<DIR>/confusions.json` を読む。ユーザーが「質問」「詳しく」「用語」の付箋を付けた文の一覧で、1件ごとに `anchor`（分からなかった文）・`question`（ユーザーの問い）・`answer`（付箋の最後の回答の冒頭）がある。ファイルがない、または空の配列なら、何も足さない。
   - **まず、その文をアシスタントが書いたかを見る。** 決まりに足してよいのはアシスタントの書き方だけ。
     - `fromSticky: true`（付箋の回答の中の文）は、いつも分岐したアシスタントの文。
     - `fromSticky: false`（本筋の文）は、本筋が「直前の回答」か「依頼文から作った説明文書」のときだけアシスタントの文。本筋がファイル（.md・コード）や diff を写したものなら、論文・README・他人のコードの文なので、決まりには足さない。
   - アシスタントの文だけを、1件ずつどちらかに仕分ける。
     - **言い方が悪かった**：英語の裸書き、略語、結論が後ろにある、前提を飛ばした、用語を説明していない、など。`anchor` の中に、その欠陥を具体的に指させる場合だけこちらにする。
     - **それ以外**：中身が難しいだけ、知識の補足を求めただけ、どこが悪いか具体的に言えないもの。決まりには足さない。迷ったら足さない。
   - `answer` は付箋の最後の回答で、ユーザーが分かったという証拠ではない。言い換えの参考にはしてよいが、それだけを根拠に「言い方が悪かった」としない。
   - `code: true` は、コードの行を選んだ付箋。コードそのものの難しさは決まりに足さない。
   - 言い方が悪かったものは、`~/.claude/japanese-style-guide.md` の「育て方」に従って、対応表の該当する節に「❌ 避ける表現 → ✅ 使う表現。理由（日付）」の1行を足す。同じ指摘の行がすでにあれば、新しい行を足さずにその行の対策を強め、日付を今日にする。似た文が何件あっても、型が同じなら1行にまとめる。
   - 足した行・強めた行を、ユーザーに短く報告する（何件の文から、どの行を足したか）。確認は挟まない。決まりのファイル自体が「指摘を受けたら応答の前に1行足す」と定めているため。足すものがなければ「書き方の決まりに足すものはありません」と一言伝える。
4. 片付ける。サーバーは「メインに送って閉じる」で自動終了している。まだ動いていれば止める。

   ```bash
   kill "$(cat "<DIR>/server.pid")" 2>/dev/null; rm -rf "<DIR>"
   ```

   寄り道の会話は残さない（ユーザーの方針：理解したらログは捨てる）。

## 注意

- アプリの中でのSQL実行は、ユーザーが付箋の「承認して実行」を押したときだけ行われる。あなたがこの手順の中でSQLを実行することはない。
- Claude Code 版では `${CLAUDE_SESSION_ID}` が使えないとき、このプロジェクトの一番新しい Claude セッションを探す。Codex 版ではこの代替は使わず、正確な親会話 ID を必須にする。
- Codex 版は付箋ごとに分岐を作り、同じ付箋の追質問ではその会話を続ける。親会話へ追記しない。「メインに送って閉じる」またはサーバーの通常終了時に、このアプリが作った分岐だけを削除する。強制終了で削除できなかった場合は `server.log` を確認し、親や無関係な会話を削除しない。
