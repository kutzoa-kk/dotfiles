# note-article-writer：メモから note の記事を作る

目的は、空き時間で続けられる負担で月1〜3万円の副収入を得ることです。読者が試行錯誤を省ける実例、判断基準、そのまま使えるテンプレートを記事にします。

役割を分けます。AI は素材の整理、切り口の提案、構成、執筆、推敲を受け持ちます。本人には、経験と結果が事実かどうかの確認と、何を公開するかの判断だけを求めます。

## 書く前に

このスキルと同じフォルダの `learned-rules.md` を必ず読みます。本人の修正から学んだ決まりが入っており、この SKILL.md の一般的な規則と食い違うときは `learned-rules.md` を優先します。冒頭の「育成フェーズ」が実施中かどうかも、ここで確かめます。

## 素材を受け取ったら

1. **短いメモでも進めます。** 素材から「誰が、どの場面で困っていて、読んだあと何ができるか」を一つに絞ります。本人が題材や例を挙げていれば、それを主題にします（「例えば〜」と挙げた例も主題の指定として扱います）。指定された範囲も狭めません。「〇〇そのもの」「〇〇全体」と言われたら全体を主題にし、その一部（素材が多い部分や新しい部分）だけを主題にしません。素材の都合で別の題材の方が書きやすいと考えたときは、書く前に一言確かめます。題材の指定がなく複数の題材が混ざっていれば、具体的な事実が一番そろっているものを選び、残りは次の記事の候補として確認事項に書きます。
2. **形式を決めます。** 指定がなければ、素材に合う形式（無料記事・有料記事・改稿）を選び、出力の冒頭で「〜なので無料記事にしました」と一言添えます。手順や記入例が一つで足りるなら無料記事、再現手順とテンプレート一式まで作れる素材なら有料記事が目安です。
3. **本文まで書きます。** 記事作成の依頼では、構成案で止めずに本文を最後まで書きます。核心となる事実が足りないときは、質問を最大2問に絞って確認事項に置き、手元の素材で書ける部分は先に書きます。足りない箇所は本文中に `【要確認：〇〇】` と空けておき、推測で埋めません。

## 事実の扱い

- 本人の経験、計測値、利用者の反応は、素材で確認できたものだけを事実として書きます。素材にない成果（「作業時間が半分に」「好評でした」など）を足しません。
- 説明のために作った例は、「例：」「記入例」のように作例だと分かる形にします。
- 外部の仕様・料金・統計を書くときは一次情報（公式文書・公式ヘルプ）を確かめ、本文に出典を添えます。確かめられなければ書かないか、確認事項に回します。
- 作業ログや文字起こしを使うときは、公開できる範囲に整えます。実名、社名、顧客名、社内の URL・パス、API キー、未公開の数字は伏せるか一般的な表現に置き換え、置き換えた箇所を確認事項に挙げます。

## 記事の形式

### 無料記事

一つの悩みに答え、読者がその場で使える手順か記入例を一つ届けます。関連する有料記事があれば（または同じ素材で作れるなら）、末尾で「有料記事では〜の一式が手に入ります」と、手に入るものを具体的に案内します。

### 有料記事

- **無料部分**：対象読者、解決できること、購入後に手に入るもの（テンプレート名や項目の一覧）を書き、見本を一つ見せます。
- **有料部分**：読者が自分で使うために必要なものを入れます。再現手順、コピーして使えるテンプレート、記入済みの実例、つまずいたときの対処です。
- **開始位置**：有料部分の直前に、前後を空行で挟んで次の1行を置きます。

```
（ここから有料部分）
```

note の有料ラインは本文の記法では指定できず、編集画面で段落の間に設定します。この行は投稿時の目印なので、確認事項に「編集画面でこの行の位置に有料ラインを設定し、目印の行を消す」と必ず書きます。価格は提案に留め、確認事項に置きます。

### 改稿

元の事実と書き手の語り口（文末、一人称、言葉の選び方）を保ちます。依頼された点に沿って、読みやすさ（段落の長さ、見出し、順序）と具体性（例・手順の補足）を改善します。事実を足したくなった箇所は本文に足さず、確認事項で尋ねます。変えた点は本文の後に3行以内でまとめます。

## 書き方

- 日本語のです・ます体で書きます。
- タイトルで約束したことを本文で必ず渡します。本文で渡せないことはタイトルに入れません。
- note に貼り付ける前提で書きます。見出しは `##`（大見出し）と `###`（小見出し）だけを使い、`#` は使いません（タイトルは別欄に入れるため）。依頼文・テンプレートはコードブロックに入れ、コピーしやすくします。
- 書き終えたら、`~/.claude/skills/stop-ai-slop/references/patterns-ja.md` の型（太字の多用、項目数の宣言、根拠のない強調、壮大な締めなど）に当たる箇所を直します。

## 出力の型

次の順で出します。

````
## 推奨タイトル
（1案）

## 本文
（note に貼り付けられる本文。有料記事なら「（ここから有料部分）」の行を含む）

## 公開前に確認してほしいこと
- （本人にしか判断できない点だけ。事実の確認、伏せた箇所、価格、有料ラインの設定など）
- （答えが要る質問は最大2問）
````

確認事項は本文の外に置き、まだ残っているものだけを挙げます。解決済みの点や一般的な注意は書きません。

育成フェーズが実施中なら、出力（推奨タイトル・本文・確認事項）を `~/.local/share/note-article-writer/drafts/<YYYY-MM-DD>-<英小文字とハイフンの短い題>.md` に保存し、最後に1行だけ「直した版を渡してもらえれば、下書きと比べて決まりに反映します」と添えます。保存先は git の外です。作業ログ由来の非公開の内容をリポジトリに入れないためです。

## 育成：本人の修正と比べてスキルを育てる

本人が直した版を渡したら、次の順に進めます。

1. **対応する下書きを特定します。** 保存先の下書きから、題や日付で対応するものを選びます。候補が複数あれば、どれかを1問で尋ねます。直した版は、貼り付けでもファイルでも受け取り、同じフォルダに `<下書きと同じ名前>-edited.md` で保存します。
2. **段落ごとに対応させて比べ、修正を分類します。**
   - 事実の訂正：その記事だけの訂正なので、決まりにしません。ただし、素材にない内容を推測で書いたことが原因なら、その書き方を避ける決まりにします。
   - 公開の判断（削った・伏せた）：どんな種類の情報を外す傾向かが読み取れれば、決まりにします。
   - 書き方の好み（語り口、語彙、文の長さ、言い切りの強さ）：決まりの候補です。
   - 構成・形式（順序、見出し、導入の長さ、有料部分の中身、タイトル）：決まりの候補です。
   - その記事だけの事情：決まりにしません。
3. **他の記事にも当てはまる形に言い換えます。** 同じ種類の修正が記事内で複数か所にある、または過去の決まりと重なるものを優先します。1か所だけで意図が読み取れない修正は決まりにせず、本人に尋ねます（最大2問）。決まりには、記事の固有名詞・数値・非公開の内容を書きません。
   - 決まりにしなかった直しのうち、他の記事でも起こりそうなもの（書き方の好み・構成・公開の判断に分けたもの）は、観察の記録 `~/.local/share/note-article-writer/observations.md` に1行ずつ残します。事実の訂正とその記事だけの事情は残しません。
   - 書き足す前に観察の記録を読み、今回の直しと同じ種類の観察が別の記事にあれば、2記事分の根拠がそろったとして決まりに格上げします。
4. **`learned-rules.md` に書き足します。** 該当する節に「❌ 避ける書き方 → ✅ 使う書き方。理由（日付）」の1行を足します。既にある決まりと同じ指摘なら、新しい行を足さずに既存の行を強め、日付を新しくします。この SKILL.md の規則そのものが本人の意図と食い違っていたと分かった場合は、SKILL.md を直します。決まりの行は合わせて60行までとし、超えそうなら似た行をまとめます。最後に「育成の記録」の表へ1行足します。
5. **報告します。** 修正の分類を短くまとめ、足した・強めた決まりと、その根拠（どの修正が何か所あったか）を示します。決まりにしなかった主な修正は、理由と、観察として残したかどうかを一言添えます。

観察の記録は、1行を次の形で書きます。git の外に置くのは、記事の中身に触れることがあるためです。

```
- 2026-11-21｜2026-11-21-ai-fix-scope.md｜構成｜冒頭の形式選定の一文を削った｜候補：形式を選んだ理由を本文の外に出す｜保留
```

最後の欄は「保留」「格上げ済み（日付）」「却下（理由）」のどれかです。

### まとめて見直す

「これまでの修正をまとめて」「決まりを見直して」と頼まれたときや、観察の保留が10行を超えたときに行います。複数のセッションで貯めたものを、ファイルから読み直して整理します。

1. `learned-rules.md`、観察の記録、下書きフォルダの下書きと `-edited.md` の組をすべて読みます。
2. 保留の観察を種類ごとにまとめ、2記事以上で重なったものを決まりに格上げします。格上げした観察は「格上げ済み（日付）」にします。
3. 決まりどうしで重なる・食い違う行を探します。重なる行は1行に統合します。食い違う行は新しい日付の方を優先し、どちらとも言えなければ本人に尋ねます（最大2問）。
4. 古い決まりが最近の直した版で守られていない（本人が逆向きに直している）場合は、その決まりを削るか書き換えます。
5. `learned-rules.md` の「育成の記録」に「まとめて見直し」の1行を足し、格上げ・統合・削除した決まりを本人に報告します。

育成フェーズの終え方：3記事続けて新しい決まりが出なければ、育成フェーズを終えるか本人に提案します。終えると言われたら、`learned-rules.md` の冒頭を「終了（日付）」に書き換え、下書きの保存と直した版の依頼をやめます。決まりは引き続き使います。

## note への入力と投稿（頼まれたときだけ）

通常の成果物は下書きまでです。ブラウザで note を操作するのは、本人が明示的に頼んだときだけです。操作は Claude in Chrome で本人の Chrome（ログイン済み）を使い、画面の手順は `references/posting.md` に従います。

頼み方で、止める位置を変えます。

- 「note に下書き保存して」：編集画面に題と本文を入れ、下書き保存で止めます。
- 「投稿して」「公開して」：公開設定の画面まで進め、最後の投稿ボタンを押す前で止めます。題、無料か有料か、価格、有料ラインの位置（目印の行の直前か）、ハッシュタグ、無料部分の最後の一文を一覧にしてチャットで見せ、本人の「はい」を待ってから押します。価格と有料ラインはこの画面で初めて確定するので、「公開して」と頼まれていても、この1回の確認は省きません。

守ること：

- 入れる本文は保存済みの下書きファイルから読みます。本人が直した版（`-edited.md`）があればそちらを使い、その場で書き直しません。
- 有料ラインを設定したら、目印の行「（ここから有料部分）」を消し、消えたことを画面で確かめます。
- note の API、トークン、Cookie は使わず、編集画面の操作だけで進めます。記事の削除や既に公開した記事の変更など、頼まれていない取り消しにくい操作はしません。
- 公開前の確認画面と投稿後の画面のスクリーンショットを保存し、報告に記事の URL を添えます。

## しないこと

頼まれていない投稿、公開、価格設定の変更はしません。

## 題材の例

最初の題材の例は「個人開発で、AI に頼んだ範囲だけ直してもらう方法」です。実際の修正1件を素材に、無料記事では依頼文の記入例を一つ紹介し、有料記事には依頼文、レビュー依頼文、完了チェックの一式を付けます。テーマは素材に応じて選びます。
