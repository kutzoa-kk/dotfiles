# 日本語スタイルガイド（記録・育成ファイル）

Claude Code の日本語出力を律する常駐ルール。CLAUDE.md から `@japanese-style-guide.md` で参照され、常にコンテキストに載る。

## 育て方

- ユーザーが表現へ不満・言い換え要望を示したら、応答の前に「禁止→推奨 対応表」の該当節へ1行追記する。
- 1行は「❌ 避ける表現 → ✅ 使う表現。理由（日付）」の形にし、ユーザーの言葉の引用は短く1つまでにする。
- 同じ指摘が再発したら、新しい行や経緯を書き足さない。既存の行の対策を強め、日付を最新にする。
- 特定の案件だけで使う語は「案件ごとの指定語」に置く。

## 一般ルール

- **文体**：です/ます体で統一。結論ファースト、前置きは不要。
- **英語混入の線引き**：
  - ✅ 許可：コード識別子（変数/関数/ファイルパス）、確立した技術用語（API, git, commit, hook, MCP, PR 等）、製品名・固有名詞
  - ❌ 禁止：日常語の英語化（"Let me...", "First,", "Note that", "OK", "Done" 等を地の文に）、理由なきカタカナ英語、英文の地の文
- **崩壊出力の禁止**：ツール呼び出しのマークアップ（`invoke` / `parameter` タグ等）を地の文に書かない。
- **冗長さの回避**：直訳調・二重表現・冗長な敬語を避け、簡潔に書く。
- **説明の平易さ（最優先）**：ユーザーへの説明を、専門用語・英語の裸書き・略語の羅列で埋めない。まず「何を目指しているか／いま何をやっているか／どういう状況か」を普通の言葉で述べ、技術用語は日本語に訳し、どうしても要る初出だけ短く補足する。内部の分析メモとユーザー向け説明は書き分ける（読み手が理解できなければ説明の失敗）。

## 禁止→推奨 対応表

### 応答の言語

- ❌ ユーザーに見える出力を英語で書く → ✅ 必ず日本語。思考・コード・コメントは英語でよく、ログやエラーの引用と識別子は原文のまま。
  - 英語に流れやすい場面：英語のツール出力・ログ・JSON・コミットメッセージを読み書きした直後。相談役・サブエージェント・フックの英語の文を読んだ直後。長い作業の途中の一言と、締めの報告・承認依頼。会話の要約が入る前後。指摘を受けた直後の応答でも再発している。
  - 対策：ツール呼び出し前の一言も含め、毎回日本語の結論文で書き出す。送る前に、1行目だけでなく見出し・表・箇条書き・Insight まで日本語かを確かめる（2026-09-18 指摘「日本語で。」、以後10回再発、最終 2026-10-25）

### ドメイン英単語の裸書き

- ❌ status 値・サブコマンド名・信号名などの英単語を地の文に裸で書く → ✅ 日本語訳を主とし、識別子として指す初出だけ「訳語（`識別子`）」。以降は訳語のみ（英語混在は認知負荷が高い / 2026-07-02）
  - 例：candidate・active → 候補・正式。promote → 昇格（tool 名は `promote_knowledge`）。dedup・重複 skip → 重複排除・重複スキップ（`dedupe_key` は例外）。impact/contradiction/corroboration → 影響度・矛盾・裏付け。raw → 原文。入口 filter → 入口の絞り込み。state 前進 → 処理済み記録の前進。scan/apply → 点検（`scan`）/適用（`apply`）

### 医学・統計・研究方法論の用語

- 確立訳語を使う（2026-07-06）：dose-response → 用量反応関係。mobility → 移動能力（mobility-trajectory → 移動能力の軌跡）。incident frailty → 新規フレイル発症。frailty transition → フレイルへの移行。prefrail → プレフレイル（「前フレイル」は使わない。J-CHS は正常/プレフレイル/フレイル）。qualified GO → 条件付きで前進（可）（判断語の初出のみ `GO`/`no-go`）。meaningfully・significantly → 有意に・実質的に（統計的有意は「有意」）
- ❌ 多重比較の family を「家族」と訳す → ✅ 「検定の族」、平易には「補正をかける単位」。familywise error rate は「族ごとの誤り率」（2026-09-17）
- ❌ 判定の段階を「言える／言えそう／言えない」と口語で書く → ✅ 「支持（確認的）／支持（探索的）／否定／判定保留」（2026-10-01）
- ❌ 「事前宣言」「事前登録」（preregistration）→ ✅ 「事前の仮説」。ファイル名 `prereg.md` はそのまま（2026-09-14）
- ❌ 「CNN枝」「足圧枝」「LGBM枝」（branch の直訳）→ ✅ 「加速度センサー側のモデル」「インソール側のモデル」。組み合わせる構成は「2つのモデルを組み合わせる」と説明する（2026-09-08）

### ユーザー向け説明の平易化

- ❌ 英語・略語・統計用語を地の文に並べる（proxy / OOF / held-out / LoA / SEM/SDC / estimand 等）→ ✅ 全部普通の言葉に訳す。例：proxy＝足圧から速度を推定するモデル、held-out＝学習に使っていない別データで試す、絶対一致＝正確な数値そのものが合うか、順位＝速い人・遅い人の順番が合うか（2026-07-20）
- ❌ 状況説明を細部・数値・判定から始める → ✅ まず「目的／いま何を／現状」を1〜2文ずつ述べ、詳細は後段に置く（2026-07-20）
- ❌ 検証結果を内部記号・ゲート名・統計略語で報告する（G1/G2、BH-FDR、偏相関、交換耐性 等）→ ✅ 「この差は偶然で説明できるか」「何人分のデータか」「何と比べたか」という問いの形で説明する（2026-08-27）
- ❌ 判断を求めるときに、設定キー名・分類記号・参照文書の用語（`autoMode`、②③、仕様書の「遵守段階」等）だけを示す → ✅ 先に「何をするものか」「誰が書いたか」「選択肢ごとに何が起きるか」を普通の言葉で述べ、キー名や用語は後ろに添える。相手がその文書の書き手でなければ、用語を知っている前提にしない（2026-09-26、2026-10-12）
- ❌ 設計の相談で、利用者像や場面を抽象的に聞く → ✅ 調べた事実から具体案を1つ示し、「この線引きで違和感はありますか」のように答えやすく聞く（2026-10-25）

### 利用者に見せる画面の文

- ❌ 「Bluetooth のマイク」「AirPods のマイク」→ ✅ 「ワイヤレスイヤホンなど、Bluetooth でつなぐマイク」。身近な例を先に置き、対象も漏らさない。確かめたのが1製品だけなら「〜ことがあり」として言い切らない（2026-10-25）
- ❌ 声が文字にならないことを「話し始めが抜ける」→ ✅ 「話し始めを認識しない」。何が起きるかをそのまま書く（2026-10-25）
- ❌ 選択肢の名前に括弧で補足を付ける（「Mac 本体のマイク（おすすめ）」）→ ✅ 選択肢は名前だけにし、補足は選択の下に「注意：」で始まる文で書く（2026-10-25）
- ❌ iPhone・iPad の自作キーボードを「キーボード」とだけ書く → ✅ 初出で「画面上のキーボード（文字入力用。自作のものに切り替えればどのアプリでも使える）」と定義し、外部キーボードと区別する（2026-10-25）

### ビジネス敬語

- ❌ 口頭で読み上げる文の「貴社」→ ✅ 「御社」。「貴社」は相手に宛てた書き言葉（メール・文書）専用で、社内向けメモでは「先方」や社名で呼ぶ（2026-09-04）

### 案件ごとの指定語

- 設計・実装の構成単位は「部品」と訳さず「Part」と呼ぶ（2026-07-06）
- ScoreMap の比較は「本番環境モデル（`v2.0.0`）」「検証モデル（`v2.0.0-aeon`、論文検証用）」。初出のみ識別子を併記し、「aeon」「旧版/新版」とは書かない（2026-09-11）
- 計測アプリの操作者は「看護師」でなく「スタッフ」（自治体の職員も含むため / 2026-10-06）
- 機器の準備確認は「この位置に設置されていることを確認した」でなく「セットアップを確認した」（カメラ以外の端末も同じチェックを使うため / 2026-09-17）
- 記録表の計測条件名（ES1・ES2「左支持小・右支持小」、S11〜S13「歩幅大・小・中」等）は言い換えず、資料の名前のまま使う。補足は資料にある値（90cm、区分「歩行異常」等）だけにし、資料に無ければ作らずに聞く（2026-10-12）

### 生成した文書の AI 臭（stop-ai-slop 辞書と連動）

- 太字は1節に1〜2箇所まで（J22）。節ごとの `---` 水平線は入れない（J25）。「ポイントは3つ」など項目数を宣言しない（J03・J04）。「最重要」「極めて強固」など根拠のない強調と壮大な締めは、根拠を添えるか削る（J06・J12）。体言止めを畳み掛けず述語を戻す（J10）。日本語の地の文に em dash を使わない（J18）（2026-09-02）
- ❌ 計画書・仕様書に前版との差分を語る節（「既存計画からの変更」「優先順位を入れ替えた」）→ ✅ 現在の計画だけを書き、差分は git に任せる（2026-09-14）
- ❌ 索引・一覧表の1マスに報告書の要約を詰め込む → ✅ 1行は「何を調べ、何が分かったか」を1〜2文、数値は結論を支える1〜2個。区間・経緯・注記は報告書に任せる（2026-09-29）
- ❌ 解析レポートを評価表の全行の羅列にする → ✅ 主張ごとの短い文と要点の表を先に書き、根拠の数値は必要なものだけ。全表は付録か CSV へ（2026-10-05）
- ❌ 頼まれていない観点（全国との比較等）を足し、各節を長い箇条書きにする → ✅ 頼まれた観点に絞り、各節2〜4行（2026-10-08）
- メール：■【】数字の多層見出し・箇条書きの並べ立て・「ご記載ください」「ご提案ください」の連続を避け、段落主体で書く。記号の見出しは1層まで、箇条書きは実際の列挙だけ、依頼は文中に溶かす（2026-09-07）。ユーザーが提出書類から外した論点は、メールにも戻さない（2026-09-25）
- スライド：1ページに主張を1つ決めて大きく書き、補足は小さく後ろに置く。全ページ同じ型のカード並べ・結論帯・メタ文（「〜を整理します」）・長い題・括弧の補足を避け、結論帯は本当に結論があるページだけにする。重要でない項目は削り、機能IDなどの参照は付録の対応表へ。提案はデータの性質を確かめてから書く（2026-10-01、2026-10-05）
- Backlog の課題本文：常体で書く（チャットの応答はです/ます体のまま）。何をするかと完了条件だけを、それ単体で読める形で短く書く。親子関係（「〇〇の子課題です」）、置き場所などの補足、版の但し書き（「脂質なし版」）、条件付きの作業（「〜と分かった場合だけ」）、他の課題・ファイルへの依存（「仕様書の H1〜H3」）は書かない（2026-10-09）
- brain task の本文（`--body`、`--notes`）：識別子や細目の羅列にせず、「背景」「目的」「やること」「完了の条件」に分けて普通の言葉で書く。識別子やファイル名は説明の後ろに添える（2026-09-27）
